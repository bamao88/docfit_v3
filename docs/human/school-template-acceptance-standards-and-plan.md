# 学校模板验收标准和改造计划

Last updated: 2026-06-17

## 当前为什么先用官方模板做验收

这里有一个重要前提：

**我们现在用学校官方模板跑测试和验收，不是因为官方模板就是最终业务要生成的模板，而是因为当前“业务生成学校模板”的路径还没有跑通。**

在真正的业务闭环里，理想流程应该是：

```text
学校规则
  ↓
系统生成学校模板
  ↓
学生论文填入模板
  ↓
最终成品 Word
```

但现在第二步“系统生成学校模板”还没有稳定跑通。为了先把验收逻辑和报告质量建设起来，我们暂时用学校官方模板来模拟“系统生成出来的模板”，让验收流程先能回答：

- 这个 Word 里哪些内容应该保留？
- 哪些内容只是说明文字，最终应该删除？
- 哪些地方应该变成学生内容的填写位置？
- 哪些内容应该由系统生成，例如目录和页码？
- 如果检查失败，报告能不能说清楚失败边界和下一步动作？

所以，当前用官方模板做验收，是一种**过渡期的开发方法**：

```text
用官方模板模拟生成模板，先把验收尺子、问题分类和报告质量打磨好。
```

它的价值是：官方模板里有大量真实学校规则、说明文字、示例内容、固定表单和样式细节，可以帮助我们提前暴露验收流程的问题。

但它也有边界：

- 不能因为官方模板通过了，就说业务生成模板已经通过。
- 不能把官方模板里的说明文字、示例文字当成最终生成模板应该保留的内容。
- 不能把“官方模板作为模拟输入时失败”直接等同于“生成逻辑失败”。
- 报告必须标明当前是在用官方模板做模拟检查，还是在检查真正的业务生成模板。

长期目标仍然是：

```text
真正由系统生成学校模板，然后用同一套验收标准检查这个生成模板。
```

在这条路径跑通之前，官方模板可以作为模拟输入，帮助我们改进验收逻辑；但它不是最终业务生成能力的通过证明。

## 最终目标和当前范围

最终目标是建立一套**Eval harness 驱动的模板生成开发流程**。

也就是说，后续开发学校模板生成能力时，不靠“看起来差不多”判断，也不靠一次性人工试错，而是按下面的循环推进：

```text
先定义学校模板应该满足什么
  ↓
运行模板生成验收
  ↓
报告说清楚哪里没满足
  ↓
只修模板生成相关问题
  ↓
再次运行验收
```

这份文档当前只约束和规划**整个项目里的模板生成这一块**。后续按这份计划修改时，默认不改这些模块：

- 不改学生内容抽取。
- 不改内容放置。
- 不改最终 Word 渲染。
- 不改真实学生论文转换链路。
- 不为了让模板生成验收变绿而放宽最终成品验收标准。

这些下游模块可以在报告里作为“背景边界”出现，但不是本轮要修的对象。

本轮真正要做的是：

```text
先把模板生成这一块的验收尺子打磨准。
```

具体包括：

- 用官方模板模拟业务生成模板，先验证验收逻辑和报告质量。
- 明确哪些失败属于模板生成验收问题。
- 明确哪些失败只是下游模块问题，暂时不处理。
- 让开发后续可以只围绕模板生成模块小步修改、小步验收。

## 先定义验收标准

这份文档先说清楚一件事：**学校官方模板不是最终要原样生成的模板，它是规则来源。**

学校官方模板通常混在一起包含这些内容：

- 学校固定要求，例如固定标题、固定标签、页眉页脚、表格结构。
- 可填写位置，例如题名、摘要、关键词、正文、参考文献、致谢。
- 示例内容，例如手写目录、示例页码、示例章节标题。
- 格式说明，例如“黑体小四”“空一行”“此处填写摘要”。
- 固定表单，例如成绩评定表、任务书、答辩记录表。
- 可选内容，例如附录、致谢、相关成果目录。

所以，验收的第一步不是问：

```text
官方模板是不是最终模板？
```

而是问：

```text
系统有没有把官方模板里的每一类内容分清楚：
哪些要保留，哪些要填写，哪些要系统生成，哪些要删除，哪些只能人工处理？
```

只有这一步分清楚以后，后面的生成模板检查才有可信标准。

## 我们到底验收什么

验收对象分成三类，不能混在一起。当前计划重点处理前两类；第三类只作为边界，不在本轮修改范围内。

| 对象 | 它是什么 | 应该怎么验 | 本轮是否改造 |
| --- | --- | --- | --- |
| 学校官方模板 | 学校给出的原始 Word，里面可能有说明、示例和固定表单 | 验它能否被拆成清楚的规则，不要求它像最终可填写模板一样通过 | 是，用来校准模板生成验收 |
| 生成模板 | 系统根据学校规则生成出来、准备承载学生内容的 Word | 验它是否保留了该保留的结构，删除了该删除的说明，留下了该填写的位置 | 是，这是最终要形成的模板生成开发入口 |
| 最终成品 Word | 学生论文放入生成模板后的结果 | 验学生内容有没有丢、位置对不对、格式是否符合学校要求、是否泄漏模板说明 | 否，本轮只保留边界，不改下游模块 |

这三类对象对应三道门，但本轮只建设模板生成相关的前两道门：

1. **规则理解门**：系统是否正确理解学校官方模板。
2. **生成模板门**：系统生成出来的空模板是否符合规则。
3. **最终成品门**：学生内容填进去以后是否合格。本轮不改它，只避免把它的问题混进模板生成验收。

当前问题的根源是：这三道门有时被混在一起检查，所以失败很多，但失败含义不够准。

## 官方模板检查的边界

官方模板检查应该判断“系统有没有理解规则”，而不是判断“官方模板本身是不是最终模板”。

检查时，每段文字、每个表格、每个位置都应该被归类。

| 类型 | 意思 | 最终生成时应该怎样 |
| --- | --- | --- |
| 固定内容 | 学校要求固定出现的文字或标签 | 保留 |
| 可填写内容 | 学生或元数据要填进去的位置 | 清空、占位，或绑定成可写位置 |
| 系统生成内容 | 目录、页码、题注编号等由系统生成 | 不保留手写示例，改成生成机制 |
| 说明文字 | 格式说明、填写说明、括号说明 | 删除，不进入最终成品 |
| 示例文字 | 学校模板里用来说明效果的示例 | 不原样保留，除非它本身也是固定内容 |
| 人工处理内容 | 成绩、签名、委员会意见等不能自动填写的表单字段 | 保留结构，字段留空或标为人工填写 |
| 可选内容 | 附录、致谢、成果目录等 | 有学生内容就生成，没有就按学校规则处理 |
| 不确定内容 | 当前规则或解析能力无法判断 | 结果必须是 `UNKNOWN`，不能当作通过 |

## 摘要区域应该是什么样

以中文摘要为例，生成模板不应该完全空白，也不应该原样保留官方模板里的说明文字。

合理目标是：

```text
摘  要：<学生中文摘要的位置>

关键词：<学生中文关键词的位置>
```

这里的 `<学生中文摘要的位置>` 不一定真的显示成这几个字。它可以是空白段落、占位符、内容控件，或者系统内部能识别的可写区域。

中文摘要区域的规则应该是：

| 内容 | 处理方式 |
| --- | --- |
| `摘  要：` 标签 | 保留，样式也要符合学校要求 |
| 中文摘要正文 | 用学生摘要替换；没有识别到时保留占位并提示人工处理 |
| `关键词：` 标签 | 保留，样式也要符合学校要求 |
| 中文关键词内容 | 用学生关键词替换；没有识别到时保留占位并提示人工处理 |
| 括号里的格式说明 | 删除 |
| 示例摘要文字 | 删除或替换，不能当成学生内容 |

英文摘要也是同样逻辑：

| 内容 | 处理方式 |
| --- | --- |
| 英文题名、Student、Tutor、学院/学校地址 | 用学生或元数据填充 |
| `Abstract:` 标签 | 保留 |
| 英文摘要正文 | 用学生英文摘要替换 |
| `Key words:` 标签 | 保留 |
| 英文关键词内容 | 用学生英文关键词替换 |
| 官方模板里的说明文字 | 删除 |

所以，摘要验收的核心不是“有没有摘要两个字”，而是：

```text
固定标签保留，学生内容可填写，说明文字剥离，样式关系不丢。
```

## 生成模板应该满足什么要求

生成模板是给后续填学生内容用的。它应该满足这些要求：

1. **结构完整**  
   学校要求的封面、声明、目录、题名信息、摘要、正文、参考文献、附录、致谢、固定表单等位置应该存在。

2. **可变内容不带错示例**  
   学生摘要、学生题名、学生姓名、正文段落等位置不能保留官方模板里的示例内容。

3. **说明文字不能泄漏**  
   “小四黑体”“空一行”“此处填写”等格式说明不能进入最终成品。

4. **固定内容不能丢**  
   学校规定必须出现的标签、标题、固定表格结构不能因为清理说明文字而丢掉。

5. **可填写位置明确**  
   系统必须知道哪里填题名、哪里填摘要、哪里填正文、哪里填参考文献。

6. **系统生成内容有生成机制**  
   目录、页码、图表编号等不能只是复制官方模板里的手写示例。

7. **人工字段不自动猜**  
   签名、成绩、评语、委员会意见等人工字段应该保留结构，但不能由系统乱填。

8. **不能证明就阻断**  
   如果系统无法判断某段内容应该保留、删除、填写还是生成，就必须返回 `UNKNOWN`，不能当作通过。

## 最终成品应该满足什么要求

最终成品 Word 是真正交给用户的结果，它应该满足：

1. 学生可见内容没有静默丢失。
2. 学生内容进入了正确的学校模板位置。
3. 旧学校封面、旧目录、旧模板前置页被正确忽略或处理。
4. 官方模板里的说明文字没有出现在最终成品中。
5. 摘要、关键词、正文、参考文献、附录、致谢等内容分类正确。
6. 目录、页码、图表编号等生成内容不是手写假内容。
7. Word 文件能被 Microsoft Word 打开，并且页面证据绑定到对应文件。
8. `FAIL` 和 `UNKNOWN` 都不能被人工视觉判断或 AI 建议改成通过。

## 当前验收质量的问题

现在的验收流程已经能暴露很多问题，但还不够适合作为稳定开发流程。主要问题是：

1. **官方模板和生成模板的角色混了**  
   有些检查把官方模板也当成“生成模板”去打分，导致失败含义不准。

2. **规则理解和生成质量混了**  
   系统还没证明自己理解了官方模板，就直接检查生成结果，开发时很难判断是规则错了还是生成错了。

3. **报告没有先告诉人失败属于哪一类**  
   现在报告会列出大量失败，但不够清楚地说“这是验收规则不准、模板生成缺口、内容抽取缺口、放置缺口，还是渲染缺口”。

4. **同一个问题在多个学生样本里重复刷屏**  
   例如同一种模板解析问题会在 9 个真实转换 case 中重复出现，增加阅读成本。

5. **coverage 更像证据包复审，不像开发入口**  
   它适合检查历史证据是否完整，但不够适合回答“我刚改完生成模板，现在下一步该修什么”。

6. **摘要这类区域的成品形态没有在报告最前面讲清楚**  
   标准里有相关规则，但产品验收入口没有先把边界讲明白。

## 改造计划

### 第 1 阶段：先把模板生成相关的两道门拆清楚

目标：让模板生成相关失败能说明自己属于哪一类，同时把下游模块问题隔离出去。

要做的事：

1. 增加“规则理解门”。
   - 输入：学校官方模板和人工审查材料。
   - 输出：系统理解到的学校规则。
   - 检查重点：固定内容、可填写位置、说明文字、示例文字、系统生成内容、人工字段是否分清楚。

2. 保留“生成模板门”，但只检查系统生成出来的模板。
   - 输入：生成模板 Word。
   - 输出：生成模板差距报告。
   - 检查重点：该保留的有没有保留，该删除的有没有删除，该可写的有没有可写。

3. 暂时不改“最终成品门”。
   - 它仍然可以报告内容抽取、放置、渲染问题。
   - 但这些问题不能混进模板生成验收结论。
   - 本轮不因为模板生成计划去修改内容抽取、放置、渲染。

验收标准：

- 官方模板不能再被当成生成模板打分。
- 生成模板失败时，报告必须说明是“生成结果问题”，不是“官方模板问题”。
- 规则理解失败时，报告必须说明是“验收尺子还没准”，不能继续宣称生成模板不合格。
- 最终成品门里的内容抽取、放置、渲染问题必须标为下游问题，不能变成本轮模板生成改造任务。

### 第 2 阶段：把内容分类规则产品化

目标：让非研发同学能看懂每个模板区域的处理要求。

要做的事：

1. 为每个学校模板区域生成一张“处理规则表”。
   - 例如封面、目录、中文摘要、英文摘要、正文、参考文献、固定表单。

2. 每个区域都标明：
   - 固定保留内容。
   - 学生填写内容。
   - 系统生成内容。
   - 要删除的说明文字。
   - 人工填写字段。
   - 缺失时怎么处理。

3. 摘要、目录、固定表单先作为示范区域。

验收标准：

- 人能从报告里直接看出“摘要最终应该是什么样”。
- 报告不只说 `element missing`，还要说“中文摘要正文这个学生内容位置缺失”。
- 任何无法分类的内容都必须进入“不确定内容”列表。

### 第 3 阶段：把报告改成开发队列

目标：报告不只是红灯，而是下一步工作清单。

要做的事：

1. 报告首页先显示失败类型：
   - 规则理解问题。
   - 生成模板问题。
   - 下游问题：学生内容抽取、内容放置、Word 渲染。
   - 证据缺失问题。

2. 同类问题合并展示。
   - 同一个模板结构问题不要在 9 个 case 里重复刷屏。
   - 把重复失败合并成“影响 3 所学校 / 9 个 case”。

3. 每类问题给出下一步动作。
   - 修规则理解。
   - 修模板生成。
   - 暂停并标记下游问题，等模板生成验收跑通后再处理。
   - 补证据。

验收标准：

- 报告首页能回答“先修哪一类问题”。
- 每个问题都能对应一个负责人或一个模块。
- 重复问题被合并，不再淹没有效信息。
- 本轮报告中的默认下一步不能把任务扩散到内容抽取、放置、渲染。

### 第 4 阶段：把生成模板验收做成小步开发入口

目标：开发每修一个模板区域，都能跑一个小检查确认进展。

要做的事：

1. 增加按学校、按区域运行的检查。
   - 例如只检查湖南农业中文摘要。
   - 只检查目录。
   - 只检查固定表单。

2. 每个区域有明确通过条件。
   - 中文摘要：标签保留、学生摘要位置存在、关键词位置存在、说明文字剥离、样式关系可证明。
   - 目录：标题保留、目录由系统生成、手写页码不保留。
   - 固定表单：表格结构保留、人工字段不乱填。

3. 每个区域支持“当前无法证明”的结果。
   - 如果缺少解析能力，返回 `UNKNOWN`。
   - 如果确定违反标准，返回 `FAIL`。

验收标准：

- 开发可以只修一个区域，不必每次面对全量 200 个失败。
- 每个区域的报告能说明“已通过、明确失败、无法证明”。
- 小检查通过后，再进入整校模板检查。

### 第 5 阶段：重新整理 coverage 的职责

目标：先为模板生成建立开发检查，再区分它和证据包复审。

要做的事：

1. 开发检查负责现场运行。
   - 用当前代码、当前输入、当前模板生成物，马上输出模板生成验收结果。

2. 证据包复审负责检查历史证据。
   - 检查 `reports` 里的文件、hash、Word 页面证据是否完整可信。

3. 两者使用同一套判断规则，但不能混用输入假设。

验收标准：

- 开发同学可以用一个命令检查当前模板生成改动。
- 产品/验收同学可以用另一个命令检查证据包是否完整。
- 不会因为历史报告过期而误判当前能力。
- 不为整理 coverage 去重写内容抽取、放置、渲染流程。

## 建议的执行顺序

1. 先实现“规则理解门”和“生成模板门”的分离。
2. 再补中文摘要、英文摘要、目录三个区域的产品化验收说明。
3. 然后改报告首页，让它按问题类型和下一步动作聚合。
4. 再做区域级小检查，让模板生成可以小步修复。
5. 最后整理模板生成相关 coverage，让它同时支持开发检查和证据包复审。

执行时的范围约束：

```text
本轮只动模板生成验收和模板生成开发入口。
如果发现内容抽取、放置、渲染问题，只记录和隔离，不在本轮修。
```

## 完成后的判断标准

改造完成后，一次失败报告应该能让非研发同学看懂：

```text
当前失败是因为：
1. 学校规则还没理解清楚；
2. 生成模板没有按规则生成；
3. 证据不够，无法证明；
4. 下游模块有问题，但不属于本轮模板生成改造。
```

并且报告应该能继续说明：

```text
这次最该先修什么，修完后跑哪一个检查。
```

这才是 Eval harness 真正转起来的标准。
